# 6. 일시(날짜·시각) 복원 가정과 정합성 검증

> **문서 목적**: `analysis.ipynb`의 CASE 4(날짜)·CASE 5(시각) 전처리가 어떤 가정 위에서, 어떤 일괄 규칙으로 수행되었는지와 그 결과를 어떻게 검증했는지 정리함.
> **기준 파일**: `analysis.ipynb` (전처리·검증·저장), `repair_cleaned.csv` (결과 13,262행 x 24열)

---

## 1. 왜 다시 정리했는가

* **문제**: 초기 전처리에서는 이상 날짜를 "가장 인접한 정상 행의 날짜"로 복사했음. 그 결과 밤에 시작해 자정을 넘겨 끝난 작업의 시작과 완료가 같은 날짜로 묶여, **완료가 시작보다 빠른 음수 소요시간**이 생김 (예: 23:11 시작, 0:11 완료).
* **보강 방향**: 오류가 보이는 케이스만 골라 고치는 방식(케이스별 땜질)은 쓰지 않음. **가정을 먼저 세우고 → 정상 케이스로 검증한 뒤 → 모든 대상 행에 같은 규칙을 적용**하는 방식으로 다시 구성함.

---

## 2. 이상 유형별로 사용하는 정보

| 이상 유형 | 데이터에서 확인되는 사실 | 사용하는 정보 |
| :--- | :--- | :--- |
| 2020~2022년 날짜 (860행) | 그 연도로만 이루어진 케이스가 없고, 케이스마다 1970년 이벤트 사이에 1~2개 행만 섞여 있음 | **시각** (날짜만 다시 정함) |
| 1905-05-23 0:00 (6행) | 6건 모두 같은 날짜·같은 시각으로 기록됨 | 없음 (날짜·시각 모두 다시 정함) |
| 일시 결측 (13행) | 날짜와 시각이 같은 행에서 함께 비어 있음 | 없음 |
| 시각 0:00 | 실제 자정 업무일 수도, 빈 값일 수도 있음 | 행마다 판정 |

## 3. 복원 가정

* **가정 A. 업무는 정해진 순서대로 일어난다.**
  * 접수(최초 접수 → 티켓 작성 → 일정 조율 → 일정 안내) → 현장(조사 → 수리 → 수리 완료 등록) → 정산(고객 안내 · 재무 전송 → 티켓 마감).
  * 고객 안내(`ReadyInformClient`)와 재무 전송(`SendTicketToFinAdmin`)은 순서 없이 **병렬**.
  * 검증: 정상 기준 케이스 398개에서, 두 정산 작업에도 순서가 있다고 보면 168건이 어긋남 → 병렬로 두면 **순서 위반 0건**.
* **가정 B. 2020~2022년 행은 날짜만 잘못 기록되었다.** 시각은 원본 그대로 사용한다.
* **가정 C. 연달아 일어나는 업무는 평소 간격만큼 떨어져 있다.**
  * 정상 기준 케이스에서 업무 쌍 사이의 간격(중앙값·최소·최대)을 계산해 사용.
  * 예: 최초 접수 완료 → 티켓 작성 시작 0분, 티켓 작성 4분, 현장조사 41분, 일정 조율 완료 → 일정 안내 0분.
  * 추정할 때는 앞뒤 업무 중 **평소 간격이 더 짧은(더 가깝게 붙어 있는) 업무**를 기준으로 삼음.

## 4. 일괄 규칙

| 대상 | 규칙 | 결과 |
| :--- | :--- | :--- |
| **[CASE 4]** 시각은 정상, 날짜만 이상 (859행) | 가정 A로 "앞 업무 이후 ~ 뒤 업무 이전" 구간을 만들고, 그 구간에서 해당 시각이 가능한 날짜를 찾음. 하나면 확정, 여러 개면 가정 C의 예상 시점에 가장 가까운 날짜 | 가능한 날짜 1개: 640행 / 예상 시점에 가장 가까운 날짜: 219행 |
| **[CASE 5]** 시각이 없거나 0:00 (28행) | 0:00이 순서를 지키고 기준 이웃과의 간격이 정상 범위(최소~최대) 안이면 유지. 아니면 가정 C로 **날짜와 시각을 함께** 추정 | 평소 간격으로 추정: 21행 / 0:00 유지(실제 자정): 7행 |

* 처음 정리했던 야간 시나리오 4가지(당일 완료 / 야간 익일 완료 / 전일 야간 착수 / 연속 현장조사)는 모두 이 규칙의 특수한 경우임. 구간이 자정을 넘으면 전날·다음 날 후보가 자동으로 선택됨.
* 대표 예시: 현장조사 시작 23:11(날짜 이상), 완료 0:11 → 시작은 완료 **전날** 23:11로 복원.
